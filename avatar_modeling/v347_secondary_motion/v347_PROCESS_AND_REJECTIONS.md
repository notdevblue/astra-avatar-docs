# v347 헤어·넥타이 움직임 — 원인과 후보 기록

실제 제작·검수 기록이다. 최종 접촉 보완은 [v348 보고](../v348_final_npr_review/v348_WORK_REVIEW.md)에 이어진다. 기존 형상·본 계층·관절 보정과 승인된 무릎·손가락 압축을 보존하며, 실제 SDK 실행 결과로 후보를 비교한다.

## 확인한 원인

넥타이는 이미 `tie_anchor → tie_01 → tie_02 → tie_03 → tie_tip` 구조와 PhysBone이 있었다. 본이 없는 문제가 아니었다. 기존 바람 클립에는 넥타이 입력이 없었다.

헤어는 본의 움직임만 작았던 것이 아니다. 원래 헤어 정점의 약 절반만 헤어 본 영향을 받았고, 면적 기준 평균 헤어 본 분담은 약 7.33%였다. 연결된 13개 헤어 부위 중 작은 12개 부위는 기존 작업의 대상에서 빠져 머리 본에 고정되어 있었다. 모든 부위를 무조건 흔들지 않고, 뿌리와 앞머리 인상을 보호하면서 뒤/옆의 긴 가닥 두 부위를 먼저 비교했다.

## 후보

| 후보 | 내용 | 판정 경로 |
|---|---|---|
| Original | 기존 PhysBone·바람·웨이트 | 같은 최신 재질에서 움직임 기준 |
| Mild | 복원력·관성 등의 약한 조정 | 원본보다 이동 반응 증가, 시각적으로 여전히 작음 |
| Medium | 더 부드러운 물리 반응 | 회전 제한 포화 없이 움직임 증가. 큰 움직임 자체를 우수함으로 보지 않음 |
| MildWind | Mild + 기존 넥타이 anchor의 바람 입력 | 없던 넥타이 바람 반응 확인, 첫 시각 검토에서 가독성은 부족 |
| ExistingBoost | MildWind + 기존 헤어 본 영향 1.8배, 상한 0.70 | 기존 가닥에서 실제 표면이 더 따라가는지 비교 |
| TailExtension | ExistingBoost + 기존 뒤/옆 두 부위에 기존 본 분담 | 뿌리 첫 20%는 고정, 끝 최대 0.60. 새 본이나 메시를 만들지 않음 |
| NprFlow | Medium 물리 + TailExtension 웨이트 + 더 읽히는 바람 | 헤어 바람 회전 2.25배, 넥타이 anchor 최대 입력 x 4°/z 8°를 바람 파라미터로 혼합 |
| NprFlowPlus | NprFlow + 기존 헤어 영향 2.8배/상한 0.80, 두 가닥 끝 0.80 | 물리와 바람은 NprFlow와 같으며 실제 표면 분담 차이를 비교 |

## 미채택 검사와 수정

첫 비교는 후보를 서로 다른 월드 위치에 나란히 놓았다. 방향 전환 결과가 위치와 섞여 과한 변위가 발생해 비교 근거로 폐기했다. 같은 원점에서 후보를 하나씩 새로 생성하는 순차 검사로 교체하고, Original을 마지막에 반복했다. 초기 GIF에서 6–9초를 정지 화면으로 유지한 방식도 최종 자료에 쓰지 않는다.

SDK의 일반 LateUpdate 이전에 캡처하면 PhysBone 결과가 반영되지 않을 수 있어 `OnFrameCompleteLate` 이후 실제 결과를 기록한다. 바람은 10초 입력과 10초 자연 복귀를 따로 확인하며, 자연 복귀 중 강제 리셋을 하지 않는다.

바람 controller를 복사할 때 이름에 Wind가 들어간 여러 마스크를 함께 바꿀 위험을 확인했다. 정확히 Gentle wind 레이어만 수정하고 Pose measurements 마스크와 관절 보정 레이어를 보존했다. Breeze/Calm 길이도 10초로 맞췄다. 여러 후보가 같은 controller를 사용할 때 복사본을 다시 삭제해 참조가 끊어지지 않도록 후보군별로 재사용한다.

Blender와 Unity 정점 번호를 그대로 대응시키지 않았다. 위치·UV·본 이름을 함께 대조하여 UV 경계의 분리 정점 모두에 같은 웨이트를 적용한다. 비대상 웨이트도 Unity 재정규화에서 1e-7 수준 차이가 생기므로, 정확 동일 대신 허용오차 내 보존으로 기록한다.

## 해석의 한계

같은 원점의 첫 HeadYaw 구간에는 반복 시 헤어 팁 약 0.9mm 수준의 재현 차이가 있다. 이를 웨이트 변경 효과로 해석하지 않는다. 본 팁 수치가 같아도 웨이트가 다르면 표면 움직임은 다를 수 있으므로 실제 렌더를 함께 본다. 콜라이더 끝점 여유와 전체 메시 관통도 서로 다른 검사다. Unity SDK 실행은 PC VRChat 클라이언트의 실제 실행을 대신하지 않는다.
